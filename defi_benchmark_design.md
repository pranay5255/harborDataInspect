# Designing a benchmark for full-stack DeFi security engineering

**Build three tasks first.** Use an automated market maker (AMM) swap whose quoted terms change before signing, a lending repayment whose receipt arrives after the app has restarted, and a vault deposit whose wallet permission must match the amount the user approved. Together they ask three different questions. Did the user authorize these terms? Did the application correctly determine what settled? How much authority and how many paid transactions did it take?

Give the model a working dapp repository, a user-reported symptom, contract source and ABI, public acceptance criteria, and a local chain. Ask for a software change. Grade the resulting application through its real browser and API entry points. The deployed contracts are fixed dependencies with seeded positions and documented behavior. The model can read them and test against them. The repaired **application** must preserve consent, balances, and access to legitimate operations for its users. A client change can only promise properties the deployed interface supports.

## What this adds to EVMbench

The published EVMbench measures detection, patching, and exploitation across 117 high-severity vulnerabilities from 40 audits. Its patch mode already checks that intended behavior survives a repair. Its replay harness already examines on-chain effects. Reuse those ideas. Change the **unit of work** from an audited contract finding to an application workflow with several independent sources of truth. The OpenAI repository points to Paradigm for maintenance. Paradigm’s companion UI accepts contract submissions for the detection evaluation. In the proposed benchmark the dapp UI itself is a subject of evaluation. [OpenAI benchmark and methodology](https://openai.com/index/introducing-evmbench/) · [Requested repository’s EVMbench README](https://raw.githubusercontent.com/openai/frontier-evals/main/project/evmbench/README.md) · [Paradigm companion interface](https://github.com/paradigmxyz/evmbench)

For example, a swap can settle successfully and the app can still have failed if the wallet request used terms different from those the trader reviewed. Conversely, a correct app may request no signature at all when the terms change. Give every such case a companion case where a valid operation **must complete**. An implementation that disables trading then fails an observable business requirement.

In the task briefs, a counted wallet request means a request for the user to sign or authorize a transaction or message. The application may read the current account and chain without consuming that budget.

**Admission rule.** Specify one money-, permission-, or settlement-related property. Identify at least two independently observable boundaries needed to establish it, such as a browser confirmation and a decoded wallet request. Supply a normal workflow that must still succeed, and show that at least one plausible incomplete repair passes local component checks and fails the end-to-end verifier. A shared-library edit may legitimately fix several layers. Count the boundaries the solution must satisfy, irrespective of the number of files edited.

## What transfers from the SWE benchmarks

The local corpus contains 1,811 task records in the primary analysis, including 186 E2E-SWE tasks. The observations below use pinned versions. The proposed DeFi tasks and their difficulty estimates are design hypotheses. [Local source manifest](data/sources.json) · [Executed EDA, especially sections 6 and 7](swe_task_eda.ipynb)

- **DeepSWE exposes why an average of passing tests is misleading.** I counted named groups in the 113 local DeepSWE 1.1 records. The median task has 44 fail-to-pass tests and 165 pass-to-pass tests, calculated separately. For 84 of 113 tasks, the regression group is larger. Across 29,196 published trials with both groups observed, the fix gate had a lower pass rate in all 65 eligible model/harness configurations. In one archived configuration the mean partial score was 0.983 while binary success was 0.628. A DeFi model could similarly pass dozens of read-only checks and miss the one wallet request that matters. Record both groups and require the critical cases individually. [Pinned DeepSWE release](https://github.com/datacurve-ai/deep-swe/tree/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9) · [DeepSWE data provenance](data/sources.json) · [Trial analysis](swe_task_eda.ipynb)
- **A realistic long task has state that survives the next stage.** DeepSWE’s Prometheus reload task requires a durable outcome after a partial application and restart, with 15 fix checks and 82 preservation checks. SWE-Marathon’s Stripe task uses a pinned SDK, repeated requests, and settlement lifecycles. Its metadata describes 12 verifier gates and gives an author estimate of 14 expert hours. Transfer durable recovery and independent client verification to a lending dashboard or a vault cutover. A longer timeout alone contributes little. [DeepSWE data provenance](data/sources.json) · [Pinned Stripe task and verifier description](https://raw.githubusercontent.com/abundant-ai/swe-marathon/7bce7b29e1f2413633eb5ed6eb10dc2efb036712/tasks/stripe-clone/task.toml) · [SWE-Marathon paper](https://arxiv.org/abs/2606.07682)
- **Test writing is a distinct engineering capability.** SWE Atlas checks whether submitted tests work on a correct implementation and detect a specified defective variant. Apply that to wallet integration conformance. A test suite that rejects a legitimate alternate adapter is itself defective. Label each task’s deliverable explicitly. In the local EDA, broad “report” and “explain” keywords incorrectly suggested a written deliverable for all 160 Atlas test-writing and refactoring tasks. [SWE Atlas](https://labs.scale.com/papers/sweatlas) · [Local grading and prompt analysis](swe_task_eda.ipynb)
- **Independent actors make coordination measurable.** SWE-Lancer uses engineer-reviewed end-to-end checks for individual-contributor tasks. The τ²-bench authors vary which actor controls part of a shared environment and evaluate coordination through ablations. Here, make the browser driver choose an intent, the wallet independently accept or decline, and the chain independently settle. All three can be deterministic. Give the same model a simpler control task to estimate how much difficulty those boundaries add. [SWE-Lancer](https://openai.com/index/swe-lancer/) · [τ²-bench paper](https://arxiv.org/abs/2506.07982)
- **Keep submissions that can be regraded.** Terminal-Bench 4.1 revised its verifiers and regraded recorded work. For a dapp, a signed-request trace is evidence about one run. Keeping the submitted source patch as well lets a corrected verifier rebuild the app and exercise a different event schedule. [Terminal-Bench 4.1 release](https://www.tbench.ai/news/terminal-bench-4-1)

## Eight candidate tasks

### 1. AMM swap after a quote refresh — build first

**Candidate-facing ticket.** “The order review sometimes shows the terms of one quote while the wallet is preparing another. Fix exact-input swaps so the trader reviews the minimum they will receive. A changed minimum requires fresh confirmation. Declining must leave the balance intact. Ordinary swaps must still settle.”

**Fixture and work.** A synthetic AMM router already enforces a minimum output. A backend returns versioned quotes, the browser shows a review, and a wallet adapter builds the transaction. Publish the unit conventions, the quote-expiry rule, and which fields require fresh confirmation. Provide a public fixture where both quote versions are valid. The defect concerns the relationship between review and submission.

**An executable example.** Seed a trader with 100 input tokens, an existing allowance, and output tokens with six decimals. The user chooses to spend 10. Quote A has a minimum of 19.80 output tokens. Quote B has a minimum of 19.55. The verifier records what the user confirmed and independently decodes the router request. On a stable A run it expects 10 input tokens spent, a minimum of 19,800,000 output base units in the request, the expected recipient, one swap, and a settled output of at least 19.80. When B replaces A *before the wallet request*, the published product policy requires another review. A user who declines B gets zero new wallet requests, broadcasts, or token movement. A user who accepts B gets one swap enforcing the newly reviewed floor. Capture the preview, the wallet request, the receipt, and both token deltas. A correct display alone cannot pass. [Uniswap swap concepts](https://developers.uniswap.org/docs/get-started/concepts/traders/swaps) · [Router interface example](https://developers.uniswap.org/docs/protocols/v3/guides/swapping/single-hop-swapping)

**Hidden variants.** Change decimal precision, response order and recipient across fixtures. Pair an expired quote with a fresh valid quote. Keep one fixed-liquidity case for exact ledger checks and one benign price movement within the accepted bound. A matched control supplies a fresh, already-version-matched quote to the wallet adapter and exercises only construction and settlement.

### 2. Lending repayment after an interrupted confirmation — build first

**Candidate-facing ticket.** “I submitted a repayment, refreshed, and now the app asks me to repay again. Restore the correct status and remaining debt after a browser or worker restart. I must still be able to make a second, separately authorized repayment.”

**Fixture and work.** Use a synthetic lending pool, existing token allowance, a browser intent, and a backend receipt indexer. Freeze interest for the first scenario. Start debt at 100 and choose a repayment of 30. The fixture mines one successful repayment before the indexer receives its notification. Restart the worker and browser with the original persistent storage. The repaired app must resume tracking with zero additional wallet requests. Compare the pool’s debt of 70 with the API and UI after the documented confirmation threshold. Capture the UI while the outcome is uncertain too. A premature “final” label is a failure even if the final number is right.

**Regression and holdout.** A separate deliberate repayment of 10 must settle and leave 60. Include a previously declined request with no mined receipt, duplicate delivery of the first receipt, and a history read by another account. A harder variant supplies a *fixture-authored* change of canonical block before finality. The external driver supplies both histories and the task specifies the finality policy. Score recovery time in simulated blocks, confirmed balances, submissions per intent, and correctness of the status history. [Ethereum receipt semantics](https://ethereum.org/developers/docs/apis/json-rpc/#eth_gettransactionreceipt) · [Block-hash-based reads](https://eips.ethereum.org/EIPS/eip-1898)

### 3. Vault deposit with an exact spending permission — build first

**Candidate-facing ticket.** “The deposit form offers ‘approve this deposit only.’ Make the permission and the deposit honor that choice, including when I change wallets or cancel between the two confirmations.”

**Fixture and work.** A fixed synchronous vault, a simple ERC-20 with declared behavior, a backend deposit planner, and a browser wallet. On the zero-allowance path a user approves exactly 25 assets for this vault and then deposits 25. Test each step. After just the approval, the on-chain allowance must equal 25, the shares must be unchanged, and the UI must accurately report the remaining permission if the user stops. After both steps, the fixture consumes the allowance and the intended recipient receives shares. Check the actual spender, asset, amount, signing account and destination chain against what the browser showed. The fixture’s token defines its approval and consumption behavior. [ERC-20 allowances](https://eips.ethereum.org/EIPS/eip-20) · [ERC-4626 deposits and previews](https://eips.ethereum.org/EIPS/eip-4626)

**Regression and holdout.** Sufficient existing allowance allows one deposit transaction. Changing accounts before the deposit must invalidate the pending review and allow a fresh review for the new account. Declining before the approval costs zero writes. Declining *after* approval preserves its actual on-chain effect. Read the raw allowance even if the UI claims cancellation. An extra paid revocation requires separate user authorization under this ticket’s policy. [Wallet account and chain events](https://eips.ethereum.org/EIPS/eip-1193)

### 4. Lending withdrawal with a consistent risk preview

A borrower needs to withdraw collateral and sees an amount available in the browser that conflicts with the pool’s assessment. Build a synthetic pool with a documented integer risk formula, fixed price and interest schedules, and a read-only account view. Give the service and UI a mix of position, price and debt reads taken at different block heights. Require each displayed estimate to correspond to one identifiable block. Publish the freshness window, the fixture’s safety margin, and the behavior when the required snapshot is unavailable.

**Grade both directions.** For a permitted withdrawal the wallet request, debited collateral, remaining debt, and displayed safety margin must agree with the verifier’s independent arithmetic at the stated block. For a known stale or inconsistent preview require a refresh or a temporarily unavailable action, zero submissions, and eventual recovery when fresh data arrives. Hold out a collateral unit change and an account already close to the policy boundary. The pool remains the authority at execution time. A price change *after* an honest review can still cause a contract rejection. Grade the app’s reporting of that outcome separately from preview correctness. [Block-specific JSON-RPC reads](https://eips.ethereum.org/EIPS/eip-1898)

### 5. Write conformance tests for a wallet adapter

Give the candidate a correct deposit adapter, an integration-test skeleton, an ABI and an explicit conformance contract. The deliverable is a **test suite**. Require it to verify that switching accounts invalidates an unsubmitted review, declining at the wallet leaves the application usable, and completing a new review yields the correct request. Publish the expected behaviors and a clean reference implementation. Keep the alternate implementations in the grader.

**Grade the tests themselves.** Run the submission against two correct adapters with different cache layouts and event batching. Both must pass. Then apply one independently written behavioral defect at a time, such as a stale account label or a “confirmed” status displayed before inclusion. Require detection of each mandatory defect with an attributable failing test. Run twice from fresh state. Report valid implementations accepted, declared defects detected, and flaky results separately. This yields a capability axis even when models can already repair the corresponding application. [SWE Atlas](https://labs.scale.com/papers/sweatlas) · [EIP-1193 provider](https://eips.ethereum.org/EIPS/eip-1193)

### 6. Claim vault proceeds within the user’s transaction budget

The app lists claimable proceeds across several positions. The deployed fixture already offers a batch-claim interface. The user chooses the eligible positions and authorizes **one paid transaction**. Build a planner, wallet confirmation and history view that complete the chosen subset within this budget. Put two settled entitlements and one pending entitlement in the fixture. Specify whether a changed eligibility set requires fresh review. Provide two independent accounts and distinguish an empty selection from an all-pending selection in the UI.

**Grade the budget and the economics together.** On the public positive case, require one request, one included successful transaction, the sum of the chosen entitlements paid to the owner, unchanged unselected positions, and matching history. On an empty or all-pending choice, require zero broadcasts and a useful status. A grader counting only gas would reward doing nothing. A grader counting only balances would accept multiple paid transactions. Hidden cases change list order, page boundaries and the eligible subset. Publish the router’s batch limit and test a selection at that limit. This is a custom fixture with its own batching semantics.

### 7. Long-horizon vault rollout with outstanding withdrawals

An operator is introducing an asynchronous redemption vault alongside a synchronous vault that already has users. Both addresses are deployed before the task begins. The team needs a release that keeps existing positions accessible, handles delayed fulfillment, and survives an interrupted index rebuild. The agent owns the frontend, backend adapters, persistent data migration, and compatibility tests. The fixture operator controls fulfillment. ERC-7540 supplies a real distinction between pending, claimable, and claimed. In the asynchronous redemption flow the standard requires the corresponding preview functions to revert. A frontend written solely around synchronous previews can pass old tests and still fail this rollout. [ERC-7540 request lifecycle and preview requirements](https://eips.ethereum.org/EIPS/eip-7540) · [Synchronous ERC-4626 interface](https://eips.ethereum.org/EIPS/eip-4626)

1. **Release with old positions.** Start from a seeded old database. The old client must still show and redeem an existing synchronous holding. The new client must discover the asynchronous vault and accurately describe delayed availability. Grade public APIs with an unmodified old client as well as with the new browser.
2. **Carry a request across release boundaries.** The user submits one redemption request. Capture its pending state. A fixture operator later marks it claimable. Only then may the client offer a claim. Check both intermediate screens, the eventual receiver’s balance, and the remaining position. Make an independent user keep a pending position throughout.
3. **Recover during backfill.** Interleave a fulfillment with a partial history backfill, restart the worker, and run the migration again. Verify that history and current entitlements converge to the canonical ledger, older positions survive, and customer wallets see no new requests from the rebuild.
4. **Exercise rollback.** Run the previous read client against the upgraded service and the rollback configuration published in the ticket. Preserve access to the old vault. Persist pending asynchronous requests so the new client can resume them after rollout restarts. Rollback capability here concerns application code and data. A completed on-chain redemption remains settled.

Use one evolving chain and database across these checkpoints. A clean start for each checkpoint would erase the behavior this task measures. Recreate the *whole sequence* for independent grading attempts. Publish the supported client versions, migration contract, allowed administrative fixture events, and required outcomes up front. Reserve event timing, initial outstanding positions, and interruption points for hidden cases. Author and time this task only after teams can grade a single redemption reliably.

### 8. Add an opt-in redemption with an enforceable minimum

Use this extension when you specifically want **Solidity engineering** in the deliverable. A fixed synchronous vault redeems shares for assets. Its ordinary redemption interface offers the app an estimate, while the product team wants a user-selected minimum amount enforced at settlement. Give the candidate permission to deploy one new, opt-in adapter and integrate it into the quote service and wallet flow. Existing deposits and shares stay at the original vault. The new feature concerns only users who explicitly select it. The standard defines the inputs and preview semantics of ordinary redemption. The minimum is an additional guarantee of this task. [ERC-4626 redemption interface](https://eips.ethereum.org/EIPS/eip-4626)

**Grade the moment the guarantee matters.** Use one fixture in which a normal simulated yield update occurs between review and execution, and one with a stable rate. When the floor is met, the authorized receiver must get at least that amount and the correct shares must be consumed. When the floor cannot be met, require zero net share and asset movement from the failed redemption, truthful status in the UI, and correct reporting of any fee for an included revert. The wallet's reviewed minimum must agree with the value enforced at settlement. Verify the successful path first, check the old vault’s code identity and legacy redemption, and record the new deployment fee separately from per-user fees. Publish how the user authorizes the adapter to use shares and seed explicit consent for any pre-authorized scenario.

**Why it makes a different benchmark item.** A frontend estimate and a backend simulation can both be accurate at the time they run. Only the settlement-layer guarantee covers a later rate change. A second correct implementation can differ in how it structures the adapter or presents the quote. The grader can accept either by observing consent, settlement and costs. Report this extension as a separate track because the authorized deployment changes what solutions are possible.

## How to build the verifier

**Separate the actors.** Use a browser driver such as Playwright to enter amounts and click the real controls. Have a deterministic EIP-1193 wallet fixture own test accounts, record requests before responding, and let the scenario choose acceptance or rejection. The backend and its indexer talk to a local EVM node. Give the verifier its own node reader, ABI decoder, expected-accounting implementation, and clock. Read API responses and accessibility-tree state from outside the submitted code. Capture the review at the instant the user consents, plus the actual request the adapter sends. An app-generated “success” log proves neither. [Wallet interface](https://eips.ethereum.org/EIPS/eip-1193) · [Ethereum JSON-RPC](https://ethereum.org/developers/docs/apis/json-rpc/)

**Control the deployment and the money model.** Fix chain ID, contract addresses, bytecode hashes, seed balances, roles, block schedule and fee settings. Use simple non-upgradeable contracts for the initial cohort. Check code identity and relevant economic state at start and finish. List expected movements, including who pays fees. Compare balances in integer base units, and compare native-currency fees separately from token quantities. Record requests, broadcast attempts, distinct transaction hashes, included successes, included reverts, and total gas used. Rebroadcasting identical signed bytes can yield the same hash. A wallet signature can be off-chain. Neither is an extra mined transaction by itself. For ordinary transactions on the fixture chain, calculate paid execution fees as the sum of receipt `gasUsed × effectiveGasPrice`, including mined reverts. Attribute customer fees to their originating signer and exclude fixture-operator transactions from the user budget. Make hard limits task-specific and public, such as one paid swap with allowance already present. Use measured gas as a diagnostic elsewhere. [Ethereum receipts](https://ethereum.org/developers/docs/apis/json-rpc/#eth_gettransactionreceipt) · [Ethereum gas and fees](https://ethereum.org/developers/docs/gas/)

**Write the expected result before the reference repair.** For each scenario specify the initial facts, user choices, external events, permitted wallet requests, economic postconditions, and latest block or tick by which displays must converge. Mark facts that must hold *throughout* separately from eventual properties. A late-corrected balance cannot repair an earlier incorrect wallet request. Author state and event assertions against documented application behavior, allow harmless variations in reads, and test a second valid implementation. Expose one complete public scenario and the policies that govern hidden variants. Hidden fixtures should change inputs and schedules within that contract.

**Package for replay in Harbor.** Put the ticket in `instruction.md`, budgets and metadata in `task.toml`, pinned dependencies and public fixtures in `environment/`, and the authoritative entry point in `tests/test.sh`. Use a separate verifier environment. Explicitly transfer the submitted patch or project artifact, apply it to a clean pinned checkout, and start the grading stack from the verifier’s own genesis and database. Run the submitted application, tests, or optional adapter in their designated runtime. Keep the verifier’s signer, chain driver, fixtures, and reward writer under separate permissions. Keep the reference repair in `solution/` for author validation. The agent may use the public stack to debug. Record the patch hash, image digests, scenario seed and verifier version so a regrade can replay the same work. Harbor documents artifact transfer and multi-service environments. [Harbor task format](https://docs.harborframework.com/tasks/overview) · [Separate verifier](https://docs.harborframework.com/tasks/separate-verifier) · [Multi-container environments](https://docs.harborframework.com/tasks/multi-container)

### Scoring and failure attribution

For a **repair task**, require the build and deployment checks, every mandatory **fail-to-pass** case, every mandatory **pass-to-pass** regression, and every applicable consent, accounting and transaction-budget invariant. On the unmodified baseline verify that each named fix case really fails and each regression really passes. Make successful, authorized execution a required case wherever the flow supports it. The **test-writing** track uses its clean-implementation and defect-detection gates. The **rollout** track requires all checkpoints on the shared history. The optional Solidity extension adds the new-deployment and settlement-floor checks. Publish each track’s score separately.

Keep a binary solve flag and a diagnostic record per scenario. Include the gate name, phase, expected and observed result, applicability, wallet requests, transaction hashes, gas, and source of evidence. Use distinct statuses for failed, passed, unreachable after a prerequisite failure, inapplicable, and harness error. If no transaction was allowed and the grader observed none, that is a measured zero. If the verifier died before observing the wallet, the count is unknown. Re-run infrastructure failures under a published retry rule and disclose unresolved ones and denominators. Publish gate rates and first divergent observation, without inferring the root cause from the terminal score.

For example, a held-out AMM run could show a correct refreshed quote in the API, a correct amount on screen, **a wallet minimum different from the one the user accepted**, and a receipt within both floors by chance. The consent gate fails even though the settlement check passes. Keep this distinction in the published trial data. Use a human or rubric for optional qualities such as the clarity of an operator handoff. Rights, quantities, fees and settled state support deterministic checks.

## A pilot that can test the claim

1. **Author three full tasks and three paired controls.** Use tasks 1–3. On the controls, respectively supply a pre-matched quote, a synchronous authoritative repayment result, and an already-resolved account/allowance plan. Retain the same DeFi arithmetic, contracts and successful end states. Give each pair a shared, verified baseline defect. For example, both AMM versions need the same unit-conversion repair, both lending versions need the same debt-unit normalization, and both deposit versions need the same exact-amount request builder. Check that each control still requires a real repair. Document which uncertainty each control removes. This gives six task configurations across three independently authored families. Scenario seeds and repeat runs do not increase the number of independent families.
2. **Validate task quality before collecting model scores.** Have a DeFi integrator write the ticket, a second engineer derive the verifier from it, and a third reviewer solve it from the public materials. Where available, mine licensed SDK changelogs, integrator support tickets or migration guides for ordinary user-visible requirements. Record provenance, author original fixtures and deploy synthetic assets. Require a passing independent solution, the expected baseline failures, a baseline-green regression group, and at least one convincing incomplete solution rejected per critical invariant. Repeat identical verifier replays and compare recorded outcomes. Resolve inconsistent or ambiguous cases before freezing the pilot.
3. **Try the same capable coding models under matched conditions.** One exploratory design is three model snapshots × six configurations × three independent agent attempts = **54 runs**. Hold harness, tools, budget and task revision fixed. Start each attempt in a fresh environment with an independent conversation. Reuse the same private evaluation schedules across models. Estimate single-attempt success (pass@1) from the fraction of independent attempts that solve each task, and weight tasks equally. Report counts by task, variation across attempts, tokens, wall time, and per-gate diagnostics. A three-family pilot can show informative failures and guide authoring, but yields weak evidence for a general model ranking. All counts here are proposed.
4. **Test whether the new dimension changes outcomes.** Compare each model’s full workflow to its paired control and inspect the exact boundary that diverged. If both fail the token arithmetic, simplify the fixture and investigate the prerequisite. If both pass all runs, add a documented lifecycle transition. If the control passes but the full workflow fails on consent or recovery, keep the family and examine alternative solutions. For a larger study, compare against EVMbench **Patch** on matched model versions and harness/budget where comparable, using published results only when those conditions are known. Correlation is exploratory. A convincing distinction also needs tasks whose checks require cross-layer evidence and actual failure examples.
5. **Expand by new engineering obligations.** Add the risk preview and budgeted claim, then the test-writing track, then the rollout. Split later development and held-out sets by *application implementation and incident family* before generating variants. Keep paired controls together. Publish author-estimated and measured human effort, plus empirical pass rates, as separate fields. Run the optional Solidity extension as a separate cohort to measure whether agents recognize which guarantees require settlement-layer enforcement. Reserve “hard” for observed, reproducible model difficulty and retain easy controls. A useful release artifact is the task-level outcome archive with replayable submissions and versioned graders. It enables exactly the kind of failure analysis that was possible for DeepSWE.

**Pilot decision.** Start with the AMM task if you can fund only one. It tests your three-system idea with one existing router, a deterministic browser decision, and one economically meaningful discrepancy a final-balance check would miss. Add lending to measure recovery over time and the vault task to measure permission scope and paid writes. Build the marathon only once all three observers can independently agree on a single user journey.
